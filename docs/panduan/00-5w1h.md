# WHAT — Apa Ini

Sistem manajemen multi-cabang untuk bisnis F&B. Satu sistem menyatukan empat fungsi:

| Modul | Isi |
|---|---|
| **Kasir/POS** | Pencatatan penjualan per kedai, dioperasikan lewat HP |
| **Stok** | Stok per kedai + mutasi antar kedai dengan persetujuan |
| **Laporan Pusat** | Omzet, perbandingan cabang, stok, pengeluaran |
| **Karyawan & Shift** | Absensi, buka/tutup toko dengan rekonsiliasi kas |

## Pemilihan Masalah

Bisnis F&B dengan beberapa cabang punya tiga keluhan yang berulang:

1. Pemilik tidak tahu omzet harian tiap cabang tanpa menunggu laporan manual
2. Stok antar cabang tidak sinkron
3. Tidak ada kontrol terpusat atas mutasi barang dan kinerja karyawan per shift

Sistem ini menyerang ketiganya sekaligus, bukan satu per satu.

## Pemilihan Fitur MVP

Keputusan yang tidak biasa: **rilis versi tipis dari keempat modul sekaligus**, bukan satu modul lengkap dulu.

Alasannya, klien pertama butuh alur kerja utuh dari ujung ke ujung — buka toko → transaksi → tutup toko → owner lihat laporan. Modul kasir yang sempurna tapi tanpa laporan tidak bisa dipakai berjualan sehari pun.

### Masuk MVP

| Fitur | Catatan |
|---|---|
| Kasir HP-first | **Wajib offline-first** |
| Pembayaran tunai & QRIS | Lewat Midtrans |
| Produk sederhana | Tanpa varian/modifier |
| Absensi QR per karyawan | Token unik per orang |
| Buka/tutup toko | Dengan hitung kas & deteksi selisih |
| Stok pcs/unit | Mutasi antar kedai wajib approval |
| Laporan pusat | Omzet, perbandingan cabang, stok, pengeluaran |

### Sengaja DITOLAK dari MVP

Ini sama pentingnya dengan daftar di atas. Kalau ada permintaan menambahkan salah satunya, keputusan menundanya sudah pernah diambil sadar:

| Ditolak | Alasan |
|---|---|
| Cetak struk fisik | Butuh hardware printer, menambah variabel kegagalan di lapangan |
| Pajak/PPN otomatis | Klien target belum PKP |
| Varian produk & resep/BOM | Melipatgandakan kompleksitas stok |
| Self-order QR meja | Bukan keluhan yang disebut klien |
| Notifikasi push | Butuh infrastruktur terpisah |
| Dark mode | Token warna sudah disiapkan sebagai CSS variable supaya bisa ditambah nanti tanpa refactor besar |
| Multi-currency | Klien target hanya Rupiah |

Prinsipnya: fokus sempit menghindari over-engineering untuk skala yang belum dibutuhkan klien pertama.

# WHY — Kenapa Keputusannya Begitu

Bagian ini yang paling penting. Tanpa memahaminya, orang berikutnya akan mengubah kode tanpa tahu apa yang dia rusak.

## Kenapa offline-first, bukan sekadar "online yang bagus"

Internet di kedai F&B Indonesia tidak stabil. Kalau kasir tidak bisa mencatat penjualan saat internet mati, mereka akan mencatat di kertas — dan data itu tidak pernah masuk sistem.

Konsekuensinya menyebar ke seluruh rancangan:

- ID transaksi dibuat di HP (UUID), bukan nomor urut server
- Transaksi ditulis ke penyimpanan lokal dulu, dikirim belakangan
- Sync harus **idempoten** — pengiriman ulang tidak boleh menggandakan data
- Shift boleh ditutup walau antrian belum terkirim

Efek samping yang menguntungkan: kalau Supabase down di jam sibuk, kasir tetap bisa berjualan tunai. Sebagian besar POS berbasis cloud mati total dalam skenario yang sama.

## Kenapa instance terpisah per klien, bukan SaaS multi-tenant

Satu deployment = satu bisnis. Tidak ada kolom `tenant_id` di mana pun.

Alasannya keputusan bisnis: sistem dijual manual per klien, tiap klien bisa di-*tuning* sesuai kebutuhannya. Membangun multi-tenant berarti membayar biaya kompleksitas di awal untuk kebutuhan yang belum ada.

Konsekuensi: menambah klien = menyiapkan project Supabase + Vercel baru. Runbook-nya di `docs/provisioning.md`.

## Kenapa Supabase

Yang dibutuhkan: database + auth + penyimpanan file + realtime. Supabase membungkus keempatnya, jadi menyiapkan klien baru cukup **satu langkah**.

Alternatif Neon (Postgres saja) sudah dipertimbangkan dan **ditolak untuk sekarang** — bagus databasenya, tapi auth, storage, dan realtime jadi tiga layanan tambahan yang harus disiapkan ulang setiap ada klien baru.

Kelemahan Supabase yang diketahui: biaya ditagih per project, jadi naik linier terhadap jumlah klien. Jadwal evaluasi ulang: klien ke-3 atau ke-4.

## Kenapa kasir tidak login pakai email/password

Kasir berganti shift beberapa kali sehari. Mengetik email dan password tiap pergantian terlalu lambat.

Karyawan login lewat **scan QR pribadi** — dua detik. Tapi konsekuensinya besar: mereka **bukan** user Supabase Auth, jadi tidak punya identitas yang bisa dibaca RLS. Pembatasan per kedai untuk karyawan harus ditegakkan di lapisan server. Lihat panduan 03.

## Kenapa stok punya ledger, bukan sekadar angka

`kedai_stock.quantity` hanya menyimpan saldo sekarang. Kalau stok fisik tidak cocok dengan catatan, tanpa riwayat pergerakan tidak ada apa pun untuk ditelusuri.

Tabel `stock_movements` mencatat setiap perubahan: kapan, berapa, karena apa, siapa. Ditambahkan **sekarang** karena menambahkannya setelah ada data produksi berarti saldo historis tidak bisa direkonstruksi lagi.

## Kenapa stok boleh minus

Kasir bisa offline dengan data stok yang sudah basi. Menolak penjualan karena catatan bilang habis lebih merugikan bisnis F&B daripada membiarkan angkanya minus lalu dikoreksi.

Ini keputusan sadar, bukan kelalaian. Jangan menambahkan `CHECK (quantity >= 0)`.

## Kenapa nomor transaksi ditetapkan server

Nomor urut per kedai per hari tidak mungkin dibuat di HP: dua kasir yang offline bersamaan pasti menghasilkan nomor sama, dan tabrakan itu baru ketahuan saat sync — setelah nomornya terlanjur disebut ke pelanggan.

Solusinya dua nomor: `local_number` sementara buatan HP (ditandai "belum sync" di layar), dan `transaction_number` final dari server.

# HOW — Bagaimana Cara Kerjanya

Bagian ini memuat kode inti yang benar-benar ada di repo. Yang belum dibangun ditandai jelas.

## 1. Design Token — satu tempat untuk semua warna

`app/globals.css`

```css
@theme {
  --color-primary: #ffd400;        /* kuning brand, tombol utama */
  --color-surface: #ffffff;        /* card, modal */
  --color-ink: #0a0a0a;            /* teks utama + semua border */
  --color-danger: #ff4b3e;         /* gagal, selisih kas, stok minus */

  --radius-md: 0;                  /* brutalism: tidak ada pembulatan */
  --shadow-brutal: 4px 4px 0 0 var(--color-ink);
}
```

Pakainya `bg-primary`, `text-ink`, `border-2 border-ink`, `shadow-brutal`.

**Jangan pernah menulis hex code di komponen.** Sistem ini dijual ke banyak klien; kalau satu klien minta warna brand berbeda, cukup ubah satu file (varian biru ada di `design_1.md`).

> Jebakan: `text-primary` = teks KUNING. Warna teks utama adalah `text-ink`. Warna solid `success`/`warning`/`danger` juga tidak boleh jadi warna teks di atas putih — pakai `text-success-text` / `text-warning-text` / `text-danger-text`.

## 2. Ledger Stok — idempotensi dijaga database

`supabase/migrations/0001_init.sql`

```sql
create table stock_movements (
  id                 uuid primary key default gen_random_uuid(),
  kedai_id           uuid not null references kedai (id),
  product_id         uuid not null references products (id),
  delta              integer not null check (delta <> 0),  -- - keluar, + masuk
  balance_after      integer not null,
  reason             text not null check (reason in
                       ('initial','sale','void','mutation_out','mutation_in','adjustment')),
  ref_transaction_id uuid references transactions (id),
  ref_mutation_id    uuid references stock_mutations (id),
  created_at         timestamptz not null default now()
);

-- Retry sync tidak bisa mengurangi stok dua kali.
create unique index movements_once_per_transaction
  on stock_movements (ref_transaction_id, product_id, reason)
  where ref_transaction_id is not null;

-- Klik approve dua kali tidak bisa memindahkan stok dua kali.
create unique index movements_once_per_mutation
  on stock_movements (ref_mutation_id, reason)
  where ref_mutation_id is not null;
```

Dua index itu inti dari keamanan data sistem ini. Idempotensi dijaga **database**, bukan pengecekan di kode aplikasi — karena jalur retry/offline justru tempat paling rawan logika aplikasi keliru.

Sudah dibuktikan: `npm run db -- supabase/tests/constraints.sql` (30/30 lulus).

## 3. Satu shift terbuka per kedai

```sql
create unique index shifts_one_open_per_kedai
  on shifts (kedai_id)
  where status = 'open';
```

*Partial unique index* — hanya berlaku untuk baris berstatus `open`. Dua shift tertutup di kedai sama tetap boleh.

## 4. RLS — pertahanan saat anon key bocor

`supabase/migrations/0002_rls.sql`

```sql
create or replace function public.is_active_admin()
returns boolean
language sql stable
security definer                    -- tanpa ini: rekursi tak berujung
set search_path = public, pg_temp   -- tanpa ini: bisa dibajak
as $$
  select exists (
    select 1 from public.admin_users
    where id = (select auth.uid()) and is_active
  );
$$;

create policy admin_all on kedai
  for all to authenticated
  using (public.is_active_admin())
  with check (public.is_active_admin());
```

`NEXT_PUBLIC_SUPABASE_ANON_KEY` dikirim ke browser — **pasti bocor**. Tanpa RLS, siapa pun yang menyalinnya dari DevTools bisa membaca seluruh data bisnis klien.

Yang diuji bukan "admin bisa baca", tapi **"user yang sudah login tapi bukan admin dapat nol baris"**. Kalau policy hanya memeriksa `authenticated`, siapa pun yang berhasil mendaftar langsung punya akses penuh.

## 5. Otorisasi dua lapis

`middleware.ts` — ringan, jalan di setiap request:

```ts
const { data: { user } } = await supabase.auth.getUser();

if (!user && !isLoginPage) {
  url.pathname = "/admin/login";
  url.search = `?next=${encodeURIComponent(pathname + search)}`;
  return redirectPreservingCookies(url, response);  // cookie WAJIB ikut
}
```

`app/admin/(dashboard)/layout.tsx` — gerbang sebenarnya:

```tsx
export default async function AdminLayout({ children }) {
  const admin = await requireAdmin();   // cek admin_users, bukan cuma sesi
  return <AdminShell adminName={admin.name} ...>{children}</AdminShell>;
}
```

Diletakkan di **layout**, bukan tiap halaman — supaya halaman baru otomatis terlindungi. Pemeriksaan per halaman cepat atau lambat ada yang lupa dipasang.

> `redirectPreservingCookies` bukan hiasan. `NextResponse.redirect()` polos membuang cookie sesi yang baru disegarkan, dan user terjebak loop login.

## 6. Tiga client Supabase

```ts
import { createClient } from "@/lib/supabase/client";   // browser, anon, kena RLS
import { createClient } from "@/lib/supabase/server";   // server, anon, kena RLS
import { createAdminClient } from "@/lib/supabase/admin"; // service role, LEWAT RLS
```

Aturan wajib untuk yang ketiga:

```ts
// ❌ mengembalikan transaksi SEMUA kedai
await db.from("transactions").select("*");

// ✅
await db.from("transactions").select("*").eq("kedai_id", kedaiId);
```

Tidak ada yang memperingatkan kalau filter itu lupa. Query pertama tetap berhasil, tetap mengembalikan data, dan kasir kedai A melihat transaksi kedai B.

`admin.ts` mengimpor `server-only` di baris pertama — build **gagal** kalau file itu terbawa ke bundle browser. Lebih baik build gagal daripada service role key terkirim ke setiap pengunjung.

## 7. Tipe TypeScript dari CHECK constraint

`scripts/gen-types.mjs` membaca daftar nilai dari CHECK dan mengubahnya jadi union:

```ts
status: "open" | "closed"
reason: "initial" | "sale" | "void" | "mutation_out" | "mutation_in" | "adjustment"
```

Efeknya:

```ts
await db.from("transactions").update({ status: "complete" })
//                                             ^^^^^^^^^^ error TS
```

Tanpa ini, typo baru ketahuan saat database menolaknya — bisa jadi di HP kasir, saat ada antrian pelanggan.

Jalankan `npm run gen:types` **setiap kali ada migration baru**. Tipe basi lebih berbahaya daripada tidak ada tipe.

## 9. Pola CRUD admin

Setiap halaman CRUD memakai empat file dengan tanggung jawab terpisah: `page.tsx` (ambil data), `actions.ts` (validasi + tulis), `<fitur>-list.tsx` (tabel), `<fitur>-form.tsx` (form modal).

Urutan wajib di setiap server action:

```ts
export async function createKedai(_prev, formData) {
  await requireAdmin();                    // 1. otorisasi -- action punya
                                           //    endpoint sendiri, UI bukan pengaman
  const parsed = kedaiSchema.safeParse(...); // 2. validasi (Zod)
  if (!parsed.success) return { error: ..., fieldErrors: ... };

  const supabase = await createClient();   // 3. tulis (kena RLS)
  const { error } = await supabase.from("kedai").insert(parsed.data);

  revalidatePath("/admin/kedai");          // 4. tanpa ini, tabel tampak
  return { error: null, ok: true };        //    tidak berubah setelah simpan
}
```

Gambar produk TIDAK lewat server action -- Next membatasi body action 1MB, jadi browser mengunggah langsung ke Storage dan hanya URL-nya yang dikirim. Detailnya di [panduan 05](05-crud-master-data.md).
